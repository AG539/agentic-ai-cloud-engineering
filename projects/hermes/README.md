# Hermes Agent Engineering Experiments

## Overview

This project documents my hands-on experimentation with **Hermes**, an AI agent environment deployed on a **Contabo VPS** and used to explore practical Agentic AI engineering workflows.

The environment combines:

* **Contabo VPS** — remote Linux infrastructure
* **Hermes** — agent runtime and orchestration layer
* **Claude Code** — AI reasoning and coding layer
* **Docker** — containerized execution
* **iron-proxy** — controlled proxy layer for sandboxed execution
* **Git/GitHub** — software development and repository workflows
* **Slack and Telegram** — communication-platform integrations

The purpose of this work is to understand how an AI agent can operate within a real engineering environment while maintaining appropriate boundaries around execution, permissions, integrations, and external actions.

---

## Architecture

The experimental environment can be represented as:

```text
Windows Workstation
        │
        │ SSH / PowerShell
        ▼
   Contabo VPS
        │
        ├── Hermes Agent
        │      │
        │      ├── Agent orchestration
        │      ├── Tool execution
        │      └── External integrations
        │
        ├── Claude Code
        │      │
        │      └── AI reasoning / coding
        │
        └── Docker
               │
               ▼
          iron-proxy
               │
               ▼
        Sandboxed execution
```

This architecture separates the infrastructure, agent orchestration, AI reasoning, and execution layers.

The main objectives of this experimentation were to:

* Explore communication-platform integrations.

* Prepare a practical foundation for future open-source and cloud-native contribution work.

## Docker Sandbox Testing

Docker sandbox execution was tested as part of the agent environment.

The objective was to investigate how potentially untrusted agent-generated operations can be executed within an isolated environment instead of giving the agent unrestricted access to the host.

The sandbox approach is important for engineering agents because commands generated by an AI system can have unintended consequences.

The experimentation therefore considered:

* Container isolation
* Command execution boundaries
* Host versus sandbox access
* Tool permissions
* Controlled execution
* Failure handling

---

## iron-proxy

`iron-proxy` was part of the controlled execution path investigated during the Hermes setup.

The proxy layer is relevant to agent security because external communication and tool access should not automatically receive unrestricted network privileges.

The architecture therefore considers the execution path as:

```text
Agent
  ↓
Docker
  ↓
iron-proxy
  ↓
Controlled external access
```

Further experimentation is required to fully evaluate the security properties and limitations of this configuration.

## Telegram Integration

Telegram integration was configured and investigated as another communication channel.

The connection process encountered a runtime problem recorded in the Hermes gateway logs:

```text
[Telegram] Failed to connect to Telegram:
Any cannot be instantiated
```

The gateway subsequently reported a failed reconnect attempt and scheduled another retry.

This integration should therefore **not be described as fully operational** at this stage.

Documenting the failure is intentional. Understanding how an agent system behaves when an external integration fails is part of the engineering work.

## Observability and Troubleshooting

The Hermes gateway logs were used to investigate integration behavior and failures.

The troubleshooting process included:

1. Inspecting gateway logs.
2. Identifying the affected integration.
3. Reading the runtime error.
4. Checking connection and retry behavior.
5. Separating configuration issues from runtime issues.
6. Recording unresolved problems for further investigation.

This reinforced the importance of observability in Agentic AI infrastructure.

An autonomous system needs sufficient logging and diagnostics for engineers to understand what it attempted, what failed, and why.

## Security Considerations

Giving an AI agent access to engineering tools introduces security risks.

The experimentation therefore considers the following principles:

### Least privilege

The agent should receive only the permissions required for the task.

### Sandboxed execution

Potentially unsafe commands should be executed within appropriate boundaries.

### Controlled network access

External communication should be restricted rather than granting unrestricted network access.

### Secret protection

API keys, authentication tokens, passwords, and other credentials must not be exposed to the public repository or unnecessarily exposed to the agent.

### Auditability

Important agent actions should be observable and recorded.

### Human oversight

High-impact or irreversible actions should require appropriate human review.

### Failure transparency

Integration failures and limitations should be documented rather than hidden.
